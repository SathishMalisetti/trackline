# Trackline background reminders

Web Push for calendar events and timed tasks, using the existing Azure Static Web Apps API and Supabase database. No native app, ActivityWatch update, laptop installer rebuild or new frontend build step is required.

## User behaviour

- In Settings, each unlocked member explicitly enables notifications on that browser/device and grants browser permission. Children receive only their own events/timed tasks. Parents receive their own plus the children they select; other parents are never included automatically.
- One reminder interval, default 15 minutes, configurable from 1 to 1440 minutes. The schedule timezone defaults to the browser's timezone; use the timezone in which the family scheduled its activities. Each device has its own settings.
- Turn off on this device unsubscribes locally and revokes the server record. Re-enable explicitly to resume. Locking or changing profiles/signing out also detaches notifications so the next member cannot receive a previous member's reminders.
- Open a saved event/task to switch “Remind this device” off/on. This setting saves immediately, affects only that device, and covers the series for recurring items. New items default to reminders; save then reopen to mute them. Cancelling a task editor does not undo an already-saved reminder switch.
- No reminder for an untimed, inactive, unapproved, completed, deleted or skipped task/event. A rescheduled occurrence uses its new date/time. A final server check in the service worker prevents a queued push from displaying stale/cancelled information.
- The notification opens Trackline through its normal login/PIN gate; push messages contain no credentials and cannot bypass permissions. Dismiss closes the notification; it does not mark a task done or disable future reminders.
- iPhone/iPad: Share → Add to Home Screen, open the icon, sign in/unlock, then enable notifications. Android/desktop: use a browser supporting Web Push and grant permission. Permission cannot be granted remotely.

## Deployment

1. Deploy the branch through the normal PR/Azure workflow. The API now pins `web-push` 3.6.7 in its lockfile. Existing `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY` settings are sufficient; never put service/private keys into frontend settings.
2. Apply `notifications/schema.sql` once, then `notifications/scheduler.sql` once in the target Supabase SQL Editor. No existing family tables/functions are replaced. The project must support the available `pg_cron` and `pg_net` extensions.
3. The scheduler targets the production origin stored in `push_config.app_origin` (the current published Azure site by default). Preview deployments intentionally cannot subscribe. If the production URL changes, update this value and the existing allowed app origin consistently.
4. The first explicit enable request generates the VAPID pair once on the server and stores it in the server-only `push_config` row. The worker credential is generated by Postgres. No extra Azure/GitHub secret copy is required. Do not regenerate VAPID keys while subscriptions exist.
5. The minute job sends no HTTP request until keys exist and someone opts in. Thus schema/scheduler can be installed before merging without sending test notifications. After installation, users enable notifications separately on each desired device.

## Architecture and safety

- `/api/push-settings` uses the existing family/email authentication and membership wrapper for settings. Children cannot select siblings; parents can select only children in their family. Subscription endpoints are restricted to the known HTTPS Apple/Google/Mozilla/Windows push hosts to avoid SSRF.
- Each browser has a random local capability. It is hashed in the database, is required to bind/revoke that browser's subscription, and cannot be used to read family data. Revocation and boolean-only delivery verification work after an account session expires. The service worker keeps the active binding/capability in IndexedDB so it works without an open page.
- Subscription tables, endpoint keys, VAPID private key and worker secret have default-deny RLS and no public/anon/authenticated table or function grants. Only server role APIs and the database scheduler use them. Family-session expiry, member/PIN/family-password changes and membership removal invalidate eligibility.
- Supabase Cron invokes `/api/push-reminder-worker` every minute with its own secret header. It does not use GitHub Actions scheduling (which is unsuitable for minute-level reminders). Azure managed APIs need no timer trigger.
- The worker reads current relational schedules, including original weekday conventions, recurrence ends, monthly clamping, fortnight anchors, skips, moved occurrences and completion logs. It uses the subscription's IANA timezone and resolves DST fall-back once at the earlier matching instant; nonexistent spring-forward times are skipped.
- Atomic delivery claims, bounded retries and leases suppress duplicate sends. Notification tags also reduce duplicate display if a process fails after a push provider accepted a message but before the database recorded success. This is best-effort delivery, not an exactly-once guarantee across the provider boundary.
- Normal scheduling precision is about one minute, with a three-minute retry/catch-up window. Only future items are sent. Provider TTL is at most five minutes and never past the activity start; the service worker verifies current validity before display. If validity cannot be verified, it does not show possibly stale information.
- No page/API caching is introduced. Sign-out clears the active worker binding, unsubscribes and closes current notifications. Normal page/browser-tab closure does not sign out or detach the subscription. Actual delivery depends on the browser/OS remaining able to receive push, permissions, connectivity and device power/background restrictions.
- Work per invocation is bounded. This first implementation targets family-app volumes (up to 100 sends / approximately 20 seconds of processing per invocation); scale the worker/queue architecture before high-volume operation.

## Operations

Inspect `cron.job` / `cron.job_run_details` for `trackline-push-every-minute`. Worker responses contain counts, never endpoint/key/payload secrets. `push_deliveries` records success/failure and bounded error codes. 404/410 push endpoints are disabled. Notification history and expired subscription records are retained; no automatic deletion policy is installed. To pause the complete service, set `push_config.enabled=false` through an administrator SQL session; per-device controls remain the normal user option.

## Verification

- `npm test --prefix api`: recurrence/timezone/DST, routing/permission/SSRF, cancellation revalidation, worker credentials and mocked sends, worker display after page closure, profile isolation and stale-message rejection.
- `node tests/security-push-sql.cjs`: isolated PGlite tables/RPCs, device ownership, claims/retries, completion/mute checks, credential invalidation and public access denial.
- `node tests/security-push-layout.cjs`: mocked parent/child settings at mobile/desktop sizes with existing themes, no login, subscription writes or real sends.
- Existing security/admin/keyboard checks continue in CI.

No production login or end-to-end device notification test is part of these checks. Physical Android/iPhone/desktop delivery needs an explicit opt-in and a separate authorised device check; wider functionality QA remains paused.
